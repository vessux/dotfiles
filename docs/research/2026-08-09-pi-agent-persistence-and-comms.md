# Pi agent persistence and communication versus local Sidekick

**Research date:** 2026-08-09  
**Decision question:** Does `pi/agent/extensions/sidekick/index.ts` duplicate an existing Pi extension/package closely enough to replace it?

**Method:** Primary sources only: Pi's bundled example and official gallery, npm registry/published package files, upstream GitHub source/READMEs, and the local Sidekick source/self-test. The initial comparison and security gate were static; the later pinned trial and permanent installation are recorded below. External URLs were fetched successfully on the research date.

## Bottom line

**Adopt pinned `pi-subagents@0.45.0`.** It is not an exact implementation-level replacement for Sidekick's warm processes, transcript forks, or cache-family tag, but the pinned trial passed the valued public workflow and no measurable need justified retaining the custom extension.

The nearest overlaps are:

- **`pi-subagents`**: strongest maintained all-round orchestration package. It adds durable run recovery, supervisor communication, and worktree isolation, but resume starts a **new** child process from a saved session rather than keeping a warm worker alive. ([gallery](https://pi.dev/packages/pi-subagents), [tool reference](https://raw.githubusercontent.com/nicobailon/pi-subagents/main/docs/tool-reference.md), [workflows](https://raw.githubusercontent.com/nicobailon/pi-subagents/main/docs/workflows.md))
- **`@agwab/pi-subagent`**: strongest match for truly detached background execution and worktrees. Its async launcher uses a detached, unreferenced worker on non-Windows systems and persists run artifacts for later status/reconciliation, but it does not provide resumable conversation sessions or warm named workers. ([gallery](https://pi.dev/packages/%40agwab/pi-subagent), [usage](https://cdn.jsdelivr.net/npm/@agwab/pi-subagent@0.4.8/docs/usage.md), [async source](https://cdn.jsdelivr.net/npm/@agwab/pi-subagent@0.4.8/src/orchestrate/async.ts))
- **`pi-subagentura`**: strongest added match for attachable workers that can survive the parent through tmux/Zellij and rehydrate from artifacts. Its ordinary async jobs are still parent-scoped, and its broader mux/workflow design is heavier than Sidekick's stdio-RPC worker pool. ([gallery](https://pi.dev/packages/pi-subagentura), [README](https://raw.githubusercontent.com/lmn451/pi-subagentura/master/README.md))
- **`@mjakl/pi-subagent`**: upstream `main` now describes named persistent child sessions, but npm/gallery still publish 2.1.0, whose documented interface is spawn/fork delegation without named continuation. Upstream `main` declares 3.0.0, so the interesting overlap is not yet the released install target. ([gallery](https://pi.dev/packages/%40mjakl/pi-subagent), [published 2.1 README](https://cdn.jsdelivr.net/npm/@mjakl/pi-subagent@2.1.0/README.md), [upstream manifest](https://raw.githubusercontent.com/mjakl/pi-subagent/main/package.json), [upstream README](https://raw.githubusercontent.com/mjakl/pi-subagent/main/README.md))

Do not add a communication package by default. Add `pi-intercom` for demonstrated live 1:1 session messaging, or `pi-messenger` only if task claiming and file reservations are also required. ([pi-intercom README](https://raw.githubusercontent.com/nicobailon/pi-intercom/main/README.md), [pi-messenger README](https://raw.githubusercontent.com/nicobailon/pi-messenger/main/README.md))

## Definitions used

These are deliberately separate:

- **Live process persistence:** the same OS process remains alive between tasks or after the parent Pi process exits.
- **Transcript/session persistence:** messages or run records survive on disk.
- **Resume after parent restart:** a later parent can continue saved child context; this may launch a new OS process.
- **Async:** dispatch returns before completion and exposes status/monitor/cancel operations.
- **Communication:** child-to-parent feedback, sibling/peer messaging, or session-to-session messaging—not merely returning one final result.

Pi itself saves sessions as JSONL and can reopen them, but a saved session does not keep an OS process alive. ([Pi sessions](https://pi.dev/docs/latest/sessions), [session format](https://pi.dev/docs/latest/session-format))

## Baselines

### Official bundled `examples/extensions/subagent/`

Pi's example launches one separate `pi --mode json -p --no-session` subprocess per delegated task. It supports single, parallel, and chained foreground calls, streams progress, and propagates abort to the child; because it explicitly uses `--no-session`, it offers neither transcript persistence nor resume. It has no background job registry, worker reuse, peer communication, worktrees, or reservations. ([official example README](https://raw.githubusercontent.com/earendil-works/pi/main/packages/coding-agent/examples/extensions/subagent/README.md), [official source](https://raw.githubusercontent.com/earendil-works/pi/main/packages/coding-agent/examples/extensions/subagent/index.ts))

Installation is manual symlinking of the example, not a gallery package install. ([official example README](https://raw.githubusercontent.com/earendil-works/pi/main/packages/coding-agent/examples/extensions/subagent/README.md))

### Local Sidekick

The source and self-test were inspected for this comparison, then retired after the replacement trial passed. The observations are retained here as research-time evidence rather than live source links.

| Capability | Local behavior |
|---|---|
| Execution/live lifetime | A named `pi --mode rpc` subprocess stays warm across multiple dispatched tasks; one task may be in flight per worker. It is stopped when explicitly requested or when the parent extension receives `session_shutdown`. |
| Transcript/session | Every worker must initialize a persistent session under the dedicated `sidekick-sessions` directory. |
| Restart resume | **No.** Session files remain, but workers/jobs are in-memory maps and `session_shutdown` stops every worker; startup has no rehydration path. |
| Fork/cache family | `sidekick_fork` forks an idle worker's session transcript and inherits its model, cwd, and `PI_SIDEKICK_CACHE_FAMILY`; the self-test checks unique child sessions with one shared family. |
| Async/monitor/cancel | `sidekick_dispatch` immediately returns a job ID; `list`, `collect`, and `stop` expose status/control. Monitoring tracks current job/tool and retains at most 12 recent activities; completed-job retention is capped and parent-visible output uses Pi's standard truncation limits. |
| Completion delivery | Completion calls `pi.sendMessage(..., { deliverAs: "followUp", triggerTurn: true })`; collection remains available for explicit waiting/full output. |
| Communication | Parent-to-worker prompts and final worker-to-parent results only; no worker-to-worker or independent-session mailbox. |
| Isolation | Shared cwd; no worktree creation, merge/apply flow, or file reservations. |

## Pinned replacement trial

A disposable RPC trial loaded only `npm:pi-subagents@0.45.0` on Pi 0.82.0, with ambient extensions, skills, prompts, themes, and context files disabled. The package registered its extension commands and bundled skill without `extension_error`, skill conflicts, or stderr diagnostics.

The public-interface acceptance workflow passed:

- Async workflows returned an ID before completion, and an ordinary uninterrupted run delivered one `subagent-notify` completion without a wait/collect call.
- Status and stop worked; completed child sessions resumed by the actual child run ID and recalled prior context.
- `contact_supervisor` woke the parent and `subagent_supervisor` accepted its reply. A coordinated child may detach from its enclosing workflow while waiting, so follow-up control targets the child run ID.
- Package-managed worktree execution left the main tree's baseline unchanged and cleaned its temporary branch; the explicit shared-tree child changed only the requested shared file. A second sequential child received the first child's output.
- A detached child remained running after the parent exited through RPC EOF. Reopening the exact persisted parent session rediscovered the child as running; stop and final stopped status then worked.

After the permanent settings switch and resource reload, a fresh no-model RPC smoke found exactly one each of `subagent`, `subagent_wait`, `subagent_supervisor`, `skill:pi-subagents`, and the local workflow skill; it found no `sidekick_*` tool, custom Sidekick extension source path, duplicate command, `extension_error`, or stderr diagnostic.

The exactly-once observation is an ordinary-run result, not a crash-consistency guarantee. The free trial model/provider made a warm-process latency comparison with Sidekick invalid; no measurable cache-family requirement appeared in the workflow, so that unique local behavior did not justify retaining a custom extension.

After permanent installation, the shared Pi npm environment reported four advisories through `context-mode@1.0.169` (`@modelcontextprotocol/sdk`, Hono, and `fast-uri`), not through `pi-subagents` or its three runtime dependencies. They were recorded but not changed as part of this migration.

## Direct feature comparison

| Feature | Sidekick | Closest existing match | Replacement consequence |
|---|---|---|---|
| Warm named worker reused across tasks | Yes | `pi-subagentura` interactive child; unreleased mjakl 3.0 has named session reuse but starts a process per call | Released packages otherwise trade warm-process latency/cache continuity for persisted resume. |
| Transcript fork into sibling | Yes, via Pi `--fork` | mjakl `fork` seeds parent context but is not a fork of a living specialist; `pi-subagents` resumes/branches runs rather than exposing Sidekick's sibling cache family | No exact released equivalent found. |
| Cache-family inheritance | Explicit family tag shared by root/forks | None documented | Unique local contract; keep if prompt-cache locality is valuable. |
| Async return + automatic follow-up delivery | Yes | `pi-subagentura` and `@agwab` have async completion modes; `pi-subagents` has rich async lifecycle | Existing packages can match dispatch, but not Sidekick's exact warm-worker plus automatic parent-turn delivery combination. |
| Bounded monitor | 12 recent activities, current job/tool, capped completed jobs/output | `pi-subagents`, `@agwab`, and `pi-subagentura` provide richer dashboards/artifacts | Sidekick is deliberately smaller; richer monitors add surface area rather than removing duplication alone. |
| Resume after parent restart | No | `pi-subagents`, `pi-submarine`; interactive `pi-subagentura`; detached `@agwab` can be rediscovered but not conversation-resumed | This is Sidekick's largest lifecycle gap. |
| Peer/session comms | No | `pi-intercom` (1:1), `pi-messenger` or collaborating-agents (mesh) | Add a comm package rather than replacing warm workers. |
| Worktrees/reservations | Neither | `@agwab` and `pi-subagents` (worktrees); `pi-messenger` and collaborating-agents (reservations) | Choose based on isolation versus shared-tree coordination; they solve different problems. |

## Recommendation matrix

| Decision | Package(s) | Choose when | Recommendation |
|---|---|---|---|
| **Retired** | Local Sidekick | Reintroduce only if a measured workload requires warm named processes, transcript sibling forks, or cache-family locality that the maintained package cannot provide. | The pinned replacement trial did not demonstrate that need. |
| **Add later** | `pi-intercom` | Independently running Pi sessions need low-latency direct request/reply, but durable offline mail and file locking are unnecessary. | Add only for demonstrated independent-session communication. |
| **Add later** | `pi-messenger` | Multiple agents share one tree and need presence, task claiming, broadcasts, and enforced file reservations. | Add only for those coordination requirements. |
| **Adopted** | `pi-subagents@0.45.0` | Durable resume, worktree handoffs, nested orchestration, supervisor communication, and upstream maintenance matter more than keeping the same warm OS process/cache family. | The pinned public-interface trial passed; keep the package version pinned. |
| **Adopt for a separate lane** | `@agwab/pi-subagent` | Jobs must outlive the parent process or need managed sandbox/worktree execution, while conversation continuation is not required. | Use only if its dedicated detached/worktree interface has demonstrated value beyond `pi-subagents`. |
| **Re-evaluate on release** | `@mjakl/pi-subagent` 3.x | A released 3.x preserves its current named-session design and gains adequate async delivery/monitoring. | Do not change the adopted package based on unreleased `main`. |
| **Adopt instead** | `pi-subagentura` | tmux/Zellij attachment, restart rehydration, child interaction, and workflows justify a larger package and mux dependency. | Closest lifecycle replacement, but not the lazy choice unless restart survival/attachment is required now. |

## Final recommendation

Adopt pinned `pi-subagents@0.45.0` and retire the custom Sidekick extension. The trial demonstrated the workflow's valued orchestration, completion, monitoring, communication, isolation, resume, and restart-recovery behavior; it did not demonstrate enough value from Sidekick's warm process, transcript forks, or cache-family inheritance to justify owning the extension.

Keep the local workflow policy as a thin `sidekick` skill backed by `pi-subagents`. Do not add a communication package by default: add `pi-intercom` only for demonstrated independent-session messaging, or `pi-messenger` for demonstrated reservations/task coordination.
