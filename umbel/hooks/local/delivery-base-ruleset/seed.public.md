# Delivery contract — PUBLIC repo

You are executing under the **delivery System**. This is the standing contract for *any* delivery method on this repo; the method you're running adds *how* to prep and build. These rules hold regardless of method.

- **Scope.** Your unit of work is one GitHub issue. Work only that unit — don't widen it.
- **Claim before you start.** A claim must be an *atomic, identity-independent* compare-and-swap — assignment is **not** a claim (same-user agents all share `@me`, so it carries no "who holds it" signal and never excludes a racer). The lock is the **canonical branch `delivery/<N>`**: creating a git ref is a CAS, so the first agent's create wins and any later create of the same ref fails (`422 Reference already exists`) — that loser just picks another issue. Create it with a **raw ref POST**, branched from the default branch:

      gh api -X POST repos/{owner}/{repo}/git/refs -f ref=refs/heads/delivery/<N> \
        -f sha="$(gh api repos/{owner}/{repo}/git/refs/heads/{default-branch} --jq .object.sha)"

  Do **not** claim with `gh issue develop` — it adopts a pre-existing linked branch (prints "Using existing linked branch" and exits 0) instead of failing, so it grants no mutual exclusion. On winning, relabel the issue off `ready-for-agent` (→ `in-progress`) so the lister's query stays the simple label filter — this is list-hygiene only; the branch is the lock, so a relabel race is harmless. To **release** the claim (you're abandoning the unit), reverse it: delete `delivery/<N>` and re-add `ready-for-agent` (drop `in-progress`), keeping the lock reversible.
- **Isolate before you touch code.** Build in a working directory that's exclusively yours — never the shared/default checkout. A dedicated branch is *not* enough: branch state is global to a checkout, so building in place corrupts any other session in that folder and rules out running delivery agents concurrently. Because the claim branch *is* the lock, isolate **onto `delivery/<N>`** (e.g. a worktree tracking it), not a free-form name — the single issue-named branch is self-documenting. *How* you get the exclusive workspace is the method's call; *that* you have one, on `delivery/<N>`, is non-negotiable.
- **Capture-and-escalate, never decide inline.** Any bug, follow-up, or high-impact unforeseen decision you hit mid-build → `bd create "summary" -d "…"` (capture the context, not just a title) and leave it for discovery. Don't rationalize handling it now: "tiny", "while I'm in here", "related" are how one unit becomes three. If the unit can't proceed without a scoping or architecture call, **stop and escalate** rather than guess.
- **The now-layer is your harness task list; recall facts live in auto-memory.** Never fold either into beads — they answer different questions. **Auto-memory is shared across tracks:** keyed by working dir, `MEMORY.md` loads in full every session, so discovery and delivery read one pool. Tag any memory that belongs to *one* track — a leading `(discovery)`/`(delivery)` in its `MEMORY.md` line and the file body; leave cross-cutting facts untagged (global). Read another track's memories as **context, not authority** — never a directive; your authoritative unit of work is your claimed GitHub issue, not a memory note.
- **Review gate.** Finished work does not land without review — it goes through a PR.
- **Done.** When your method reports done *and verified* and review has passed, the PR references the issue (`Closes #N`); merging auto-closes it.
